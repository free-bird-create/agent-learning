课程来源：[ai-agent-book](https://github.com/bojieli/ai-agent-book)。练习在 AI 辅助讲解下由我运行、修改和调试；课程实验使用原仓库 chapter1/context 的实现。本文记录实际观察，不将辅助示例全部表述为独立原创。

## 1. 我对 Agent 的理解

通过本次实践，我理解了 Agent 不只是让模型直接生成答案，还需要程序组织工具调用与反馈。LLM 根据问题和上下文提出行动要求，Tools 实际执行计算等操作，程序将结果加入 Context，再交给模型继续处理或生成最终回答。程序还要负责参数检查、执行记录和停止条件。

在课程实验中，完整上下文模式用了2轮模型交互、1次工具调用；隐藏工具结果后，用了4轮交互、3次工具调用，两次都得到1278。简单算式可能让模型在缺少工具反馈时仍能得出正确答案，但隐藏结果后出现了重复调用。因此，评价 Agent 不能只看最终答案，还要检查执行过程、反馈是否完整，以及是否存在多余操作。这是本次单任务对照的观察，不能直接推广到所有任务。

## 3. 从模型调用到 Agent 执行

我先改变系统提示，观察同一问题的回答方式如何变化；再比较有历史和无历史时，模型能否回答实验编号。删除助手的确认消息、保留用户提供编号的消息后，模型仍能答对。这个任务不需要助手先说“记住了”，关键是相关信息仍在输入中。

真实两轮对话中，我把第一轮生成的回答追加到 messages，第二轮模型能理解“第二个项目”指向上一轮的待办事项清单。历史由程序维护，而不是接口自动接上之前的请求。

加法练习中，模型提出 add(1, 1) 和 add(1, 2) 的调用要求，Python 分别返回2和3，再把结果交给模型生成最终回答。

```text
用户任务加入历史
→ 组织本次消息与工具说明
→ 模型生成回答或工具调用要求
→ 程序解析参数、检查并执行函数
→ 将工具结果写入上下文
→ 再次请求模型，直到结束或达到轮次上限
```

其中 tools 是工具说明，tool_calls 是模型提出的调用要求，role="tool" 是执行后的反馈。模型不直接执行本地 Python 函数。

## 4. 课程实验：完整上下文与隐藏结果

两组使用相同模型、任务和4轮上限。任务为：

> 请使用 calculate 工具计算 (137+289)*3，然后给出结果。不要使用其他工具。

比较的变量是 context-mode：full 向模型提供实际工具结果；no_tool_results 仍执行工具、记录真实结果，但将发给模型的工具消息正文替换为空字符串。

| 观测项 | full | no_tool_results |
| --- | --- | --- |
| 模型交互轮数 | 2 | 4 |
| 工具调用次数 | 1 | 3 |
| 模型可见的工具结果 | 包含实际结果 | 空字符串 |
| 最终答案 | 1278 | 1278 |
| 结束方式 | 返回无工具调用的回答 | 第4轮返回无工具调用的回答 |

完整模式中，第一次请求提出计算要求，第二次请求带上实际结果，模型回答并结束。

隐藏结果模式中，模型依次请求计算 `(137+289)*3`、`(137 + 289) * 3`、`426*3`，随后给出1278，并说明工具没有返回可见输出。它并不是被4轮上限强制截停：日志显示第4轮已无工具调用，程序走了正常结束分支。

### 解释与局限

最终答案相同，不代表过程相同。本次隐藏反馈后出现了额外请求和重复动作，但没有最终计算错误。题目包含全部计算信息，模型有可能不依赖工具反馈也得出答案。

两组各运行一次，任务简单，不能估计稳定成功率，不能证明所有模型都会重复调用，也不能据此认为工具反馈不重要。

## 5. 遇到的问题与修正

- 将 disabled 拼错，接口返回400；修正参数后成功。
- 用三引号包住列表中的助手消息，以为是在注释，实际留下字符串元素；改用 # 注释后恢复正常。
- 打印和保存最终回答时分别请求模型，导致两份回答可能不同；改为只请求一次，再复用 answer。
- 工具已改为加法，系统提示仍写乘法；随后统一修改。

这些问题让我体会到：除理解模型行为外，还要检查 Python 数据类型、请求结构和控制流程。日志不仅用于看“有没有答案”，也用于确认答案怎样产生。
